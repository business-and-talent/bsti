# BSTI Production Package and Launch Gates Design

**Status:** Founder-approved

**PR:** #9｜Production Package and Launch Gates

**Baseline:** `main` at `4700e61db1c19b9fc84908fa3529c030729b17e4`

## 1. Goal

Create a repository-controlled, deployable BSTI package for the future production path at `https://richboss.com/bsti/`, while keeping all real-data submission disabled until ICP filing and the remaining launch gates are complete.

PR #9 prepares the package and the manual activation boundary. It does not deploy to Tencent Cloud, change DNS, bind a domain, create production infrastructure, or collect real customer data.

## 2. Frozen Domain and Path Rules

- Brand mother domain: `richboss.com`.
- Chinese-language-friendly entry domain: `fulaoban.cn`.
- `fulaoban.cn/<path>` will later use a path-preserving permanent redirect to `richboss.com/<path>`.
- BSTI canonical path: `https://richboss.com/bsti/`.
- BSTI submission API path: `https://richboss.com/api/v1/assessments`.
- Rich Boss Playbook paths remain outside PR #9.

No DNS or redirect mutation occurs in this PR.

## 3. Package Shape

A deterministic build command creates:

```text
dist/
├── bsti/
│   ├── index.html
│   ├── privacy.html
│   ├── report-usage.html
│   ├── runtime-config.js
│   └── submission-client.js
└── deployment-manifest.json
```

The source `index.html` remains the GitHub Pages demo. The build script copies it and injects only the production-package runtime scripts and submission hook into the copied file.

This avoids restructuring the existing single-file product and avoids connecting GitHub Pages to the write API.

## 4. Runtime Configuration

The public runtime configuration contains no secrets:

```js
window.__BSTI_RUNTIME_CONFIG__ = Object.freeze({
  environment: 'production-ready',
  submissionEnabled: false,
  apiBasePath: '/api'
});
```

Default is always `submissionEnabled: false`.

When disabled:

- the browser makes no assessment submission request;
- the page continues to display a visible not-yet-launched notice;
- users must not enter real personal or enterprise data.

A future enabled build requires an uncommitted release-approval JSON file proving every launch gate. The build must refuse `--enable-submission` when the approval file is absent, incomplete, expired, or contains placeholders.

## 5. Frontend Submission Flow

The existing browser compiler remains authoritative.

On the final action:

```text
score answers in browser
→ compile BSTM report in browser
→ show report immediately
→ submit the normalized operational payload when enabled
```

The network request never blocks report display.

### Success

Show a low-friction status:

```text
资料已安全保存
```

Then remove the pending payload from browser storage.

### Failure

Keep the report visible and show:

```text
报告已生成，但资料尚未保存。
[重新保存]
```

Retry uses the same `assessmentId` and exact payload. PR #8 idempotency handles identical retries without duplicate records.

## 6. Pending Payload Boundary

Before the request, store one pending submission in browser `localStorage`:

- request payload;
- creation timestamp;
- current status.

Remove it immediately after a successful response.

A pending payload older than seven days is discarded. No account, cross-device recovery, cloud draft, report history, or server-side draft is added.

The existing report continuation hash remains unchanged and continues to contain only the data already defined by the browser report continuation contract.

## 7. Request Mapping

The browser maps the existing state to the frozen PR #8 request contract:

- schema: `bsti-assessment-submission-v1`;
- instrument: `BSTI-40`, `V0.4.3`;
- UUID v4 generated by the browser;
- existing profile codes only;
- required report-processing consent and version;
- optional marketing consent and coherent version;
- 40 answers mapped by instrument order to numeric `itemId` values `1` through `40`.

The client does not score, compile, reinterpret, or add research consent.

## 8. Launch Gates

The machine-readable launch-gate contract contains these required gates:

1. ICP filing for `richboss.com` complete and valid for the operating entity;
2. registered operating legal entity confirmed;
3. personal-information rights contact confirmed;
4. Tencent Cloud contracting entity confirmed;
5. production CloudBase environment in Shanghai confirmed;
6. production MySQL target confirmed empty before first migration;
7. backup and restore procedure verified;
8. vendor and data-flow inventory approved;
9. privacy and report-usage text finalized with no placeholders;
10. HTTPS, `/bsti/*`, and `/api/*` routing verified;
11. final legal review approved;
12. named release approver and approval time recorded.

Current status is not represented as approved in the repository. ICP filing is explicitly incomplete.

## 9. Build Manifest

`deployment-manifest.json` records:

- source commit supplied by the operator or CI;
- build timestamp;
- BSTI version `V0.4.3`;
- BSTM version `V0.4.4.1`;
- canonical domain and paths;
- submission-enabled state;
- privacy and report-usage versions;
- launch-gate contract version.

It contains no credential, database host, private network address, environment ID, or customer data.

## 10. CI Verification

PR #9 CI must prove:

- the disabled package builds without external credentials;
- `/bsti/` relative links remain valid;
- runtime scripts are injected before the existing module application;
- report rendering occurs before submission starts;
- disabled mode performs no request;
- enabled test mode creates the exact PR #8 payload;
- success clears the pending payload;
- failure retains it and exposes retry;
- identical retry keeps the same UUID and payload;
- enabled package creation is rejected without complete approval evidence;
- the artifact contains no secret patterns or real environment identifiers;
- all existing BSTI, BSTM, backend, and MySQL contracts remain green.

CI may upload the disabled `dist/` directory as an artifact. CI does not deploy it.

## 11. Explicit Exclusions

PR #9 does not:

- apply for ICP filing;
- create or purchase Tencent Cloud resources;
- run production migrations;
- store production credentials;
- modify DNS or domain registration;
- bind `richboss.com` or `fulaoban.cn`;
- enable production submission;
- replace privacy placeholders with guessed information;
- add login, CRM, payment, report cloud storage, Eliy interpretation, research export, or Playbook pages;
- modify `BSTI-40 V0.4.3` or `BSTM V0.4.4.1`.

## 12. Completion Boundary

PR #9 is complete when the repository can produce and verify a disabled deployable package and can refuse unauthorized activation.

Actual production activation is a separate operator action after the required evidence exists. Until then, both frontend and backend submission switches remain off.
